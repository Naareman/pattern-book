Tracing

A trace is a time-stamped record of each step a request passed through: which model, which prompt, which tools, which documents, how long each piece took.

01What It Is

A receipt for every step.

A trace stitches every step of a single request into one ordered story (spans for the prompt, the model call, the documents, the tools, and their timings) so you can open any answer and see the exact path it walked to get there.

03Where It Fits

How it relates to nearby ideas.

What it is
The raw record of what happened. The runtime emits the steps. A viewer puts them in order. Anyone can open a past request and read it back step by step.
Sits next to
Pairs with replay (re-running an old request), attribution (asking why this answer came out), and cost tracking (adding up the spend per step).
04When It Matters

When to reach for it.

  • A user reports a strange answer and you want to open that exact request and look inside.
  • One step is slow and you want to see which one, and how often it is the same culprit.
  • You need a clear audit trail of which prompt, which model, and which documents shaped each answer.

Sources

  • Sigelman, B. et al. (2010). Dapper, a large-scale distributed systems tracing infrastructure. Google Technical Report. The paper that introduced spans, trace ids, and the parent-child shape that became the standard for production tracing.
