Constrained Decoding

Mask out every token the model is not allowed to produce, so invalid output is structurally impossible.

01What It Is

Validity enforced at the token level.

Constrained decoding works by running a grammar or finite-state machine alongside the model's forward pass. At each decoding step, the grammar says which tokens are legal continuations given what has been produced so far. All other token probabilities are forced to zero (masked) before sampling. The result is that the model can never produce text that violates the grammar, regardless of what the prompt says or what the weights prefer. Common grammars used in practice are JSON, EBNF rule sets, and regular expressions. Libraries such as Outlines and llama.cpp's grammar support implement this for open models; hosted APIs surface it as structured output modes.

03Where It Fits

Its place in the taxonomy.

L4
Home layer
Output Shape & Decoding sub-axis. The grammar runs inside the single call, modifying the token distribution at each step before sampling happens. Everything is inside one model call.
L4
Neighbor
Schema Enforcement is the higher-level cousin: it specifies what fields and types are required. Constrained Decoding is the mechanism that can enforce such a schema at the byte level. The two often work together.
L0
Cross-reference
Grammar-masked decoding is often implemented in the serving runtime (L0). The concept and design decision live in L4; the execution lives in L0 infrastructure.
Filing rule: Shapes the model's output within a single call. The grammar runs as part of decoding, not as a second call or a separate model.
04When It Matters

Who needs this.

Teams running open models where they control the serving stack, and any system where a malformed response causes a hard failure (a database write, a downstream API call, a safety check). Schema Enforcement via prompting gets you most of the way there; constrained decoding gives you the last-mile guarantee that not even an unusual input can produce an invalid token sequence.
