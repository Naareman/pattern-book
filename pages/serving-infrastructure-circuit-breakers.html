Pausing a failing service

When a model or tool starts failing, stop sending it requests for a short while. Check back gently. Resume only when it answers cleanly again.

01What is it?

A switch that trips.

Borrowed from the fuse box on a wall: a circuit breaker watches how many calls to a model or tool are failing. Once the failure rate crosses a line, the breaker trips and the system stops calling that service for a short pause. After the pause, it tries one careful test call. If that works, the breaker closes and traffic flows again. If it fails, the pause restarts.

02An Example

Three states the switch moves between.

A model API has been returning errors. The breaker walks through three states to protect the system and let it recover.
Closed
Traffic flows. The breaker is counting failures in the background.
→
errors pass the line
Open
All calls return a fast error for 30 seconds. The struggling service gets room to recover.
→
pause ends
Half-open
One test call goes out. If it succeeds, go back to closed. If it fails, open again.
Why pause at all: a struggling service that keeps getting hammered by retries usually stays down longer. The breaker hands it a quiet minute so it can come back.
03Where It Fits

Where it sits.

Pairs with
A fallback chain. The breaker decides "this service is sick"; the chain decides what to do instead.
Pairs with
Retries. The breaker stops retries from piling on a service that has already given up, by sending a fast error instead of trying again.
Not the same as
Rate limiting. A rate limit caps how many calls you make on a healthy service. A breaker reacts to a service going sick.
04When It Matters

When to reach for it.

  • You call an outside model or tool that can go down or slow to a crawl, and your app freezes whenever it does.
  • You want to stop one sick service from dragging the whole product down by holding every request hostage in a long wait.
  • You have a fallback ready and want a clean signal for when to use it, instead of guessing every call.
