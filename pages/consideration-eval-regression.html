Regression testing

Re-run the same fixed test cases on every change, so the moment something that used to pass starts failing, you see it.

01What It Is

Catch a quiet step back.

Regression testing runs the same frozen golden set on every change to the system: a new prompt, a new model, a new retrieval index, an upstream library bump. Each case has a known good answer. If a case that used to pass starts failing, the run is blocked until someone explains why. The whole point is to catch the silent step backwards: a tweak that helps 20 cases while breaking 3 others, where the average score barely moves.

02An Example

A prompt tweak quietly breaks two cases.

Run: prompt v2.1 vs prompt v2.2 on the support-bot golden set
v2.1 (yesterday)
case_017 refund windowPASS
case_032 multi-currencyPASS
case_044 cancel orderPASS
case_058 invoice resendPASS
case_091 escalation rulePASS
v2.2 (today, after tweak)
case_017 refund windowPASS
case_032 multi-currencyFAIL
case_044 cancel orderPASS
case_058 invoice resendPASS
case_091 escalation ruleFAIL
Pass-rate: 120/120 → 118/120. Average score moved less than 2%. The two newly failing cases are blockers until reviewed.
Watching the average alone would let this through. The per-case run shows exactly which two questions to investigate.
03Where It Fits

How it relates to nearby ideas.

What it is
A discipline: every change runs against the same test set, and any drop on a passing case blocks the change.
Pairs with
A versioned golden set, a continuous integration pipeline, and an eval-driven workflow where the test suite grows with every bug fix.
04When It Matters

When to reach for it.

  • You ship changes often: every prompt edit, retrieval tweak, or model bump can quietly break a corner case.
  • Customers report a bug: add it to the regression suite so the same break can never sneak back in.
  • You depend on a third-party model: provider updates change behaviour, and a regression run is your early warning.
