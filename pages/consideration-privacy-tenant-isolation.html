Tenant isolation

Each customer's records, prompts, and search results live in a sealed lane. A query from customer A only ever returns rows that belong to customer A.

01What is it?

What is it?

Tenant isolation stamps every record with its owner's ID and filters on that ID at the lowest level of the stack, so the model never even sees another tenant's data because the search step already rejected it.

02An example

Pick a tenant. See what gets through.

Two companies use the same search index. Each query carries the asking tenant's id. The index returns only matching rows.

SELECT * FROM docs WHERE tenant_id = 'acme' AND text MATCH 'pricing policy'
Rows the index returns
The filter runs in the index, not the model. Even a stray phrase like "tell me about Globex" comes back empty for Acme, because Globex rows were never read.
03Where it fits

How it relates to nearby ideas.

What it covers: the wall between customers. A single shared model is fine: a single shared data path is the bug. Isolation lives at the data and search layer, under every model call.
Sits next to: deciding what one user inside a customer can do is the next step in (access control). Isolation puts each customer in a sealed lane. Access control sets the rules inside that lane.
Quick test: if you ran the same query for customer A and customer B, would the results overlap by even one row? If yes, isolation is broken.
04When it matters

When to reach for it.

  • Several customers share one running app: a B2B SaaS, a multi-tenant agent, or a hosted assistant.
  • You use a shared search index or memory store across customers to save cost.
  • A leak across customers would be a deal-ending event: medical, legal, financial, defense.
