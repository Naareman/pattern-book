Eval-driven development

Write the test case first, then change the system to pass it. Every improvement becomes a new case the system can never lose.

01What It Is

Test first, change second.

Eval-driven development borrows the idea behind test-driven coding. When a bug is reported or a new behaviour is wanted, the first move is to add a case to the golden set that captures it, with the answer you would have wanted. Only then do you change the prompt, the retrieval, or the model. The change is done when the new case passes and every old case still passes. The eval set grows with every fix, so the system is steadily protected against ever losing that ground again.

02An Example

A bug report becomes a permanent test.

Customer reports: "the bot got the refund window wrong"
01 Add a case "What is the refund window?" with the answer "30 days from purchase."
→
02 Run the eval The new case fails. Every old case still passes.
→
03 Change the system Edit the policy prompt to include the refund window.
→
04 Re-run New case passes. Old cases still pass. Ship.
↵ The new case stays in the suite forever, so this bug can never come back unnoticed.
Every reported issue ends as a fix and a test. The suite grows with the product.
03Where It Fits

How it relates to nearby ideas.

What it is
A workflow that turns every product decision into a test case before any code or prompt changes.
Pairs with
A versioned golden set that the suite writes to, and a regression run that re-checks every old case on every change.
04When It Matters

When to reach for it.

  • The team iterates fast: many prompt tweaks per week, with several people changing the system at once.
  • Quality keeps oscillating: a fix lands, then a regression appears next week. Capturing each fix as a test ends the loop.
  • You want product, engineering, and the domain expert to share one source of truth for what the system is supposed to do.
