Reusing stored answers

When a request looks like one you already answered, skip the model and serve the saved reply.

01What Is It?

Answer once, then serve it again.

Before sending a request to the model, the system checks a store of past requests. If the same one (exact match) or a very close one (meaning match) is already there, return that saved answer. No model call. No new cost. Two flavors: exact-prefix caching reuses the start of identical prompts so the model only pays for the new tail, and semantic caching matches by meaning so "how do I reset my password" hits the cached answer for "I forgot my password".

03Where It Fits

How it sits next to other ideas.

What it shapes
The runtime checks the cache before the call goes to the model. If it hits, the model never runs for this request. If it misses, the call proceeds and the new answer is stored for next time.
Two parts
The check itself sits with the runtime here. The contents (what got stored, when it expires, when to invalidate) live with the data and artifact lifecycle, because the cache is a piece of data the runtime reads.
04When It Matters

When to reach for it.

  • Many users ask the same small set of questions: support FAQs, product info, common how-to.
  • Cost per call is real and traffic is high enough that even a 20% hit rate pays back.
  • Answers do not change minute by minute. Cached replies stay correct for hours or days.
  • Be careful when answers depend on the user, the time, or live data. Then either skip the cache or scope it tightly.
