Prompt lifecycle thinking

Treat the prompt like code: every version has an ID, a score on the same eval, and a clear path to roll back when a new one underperforms.

01What It Is

A prompt is a versioned asset.

Prompt lifecycle thinking is the habit of treating each prompt as a tracked artifact rather than an inline string. Every version has an ID, an author, a date, and a score on the same eval set. New versions are scored before they go live. Live traffic records which version answered which request, so a quality dip can be traced to a prompt change in minutes, and rollback is a one-line switch back to the last good version.

02An Example

A prompt with its history.

prompt: support_reply · eval set: support_v3 (200 cases)
v1.0 First draft. Tone reads as too formal. 81.2% Retired
v1.1 Added a friendly opening line. 84.5% Retired
v1.2 Added a clear refund policy section. Current live version. 88.1% Live
v1.3 Tighter wording. Dropped a needed example. 85.7% Blocked
v1.3 fell below v1.2 on the eval, so it was blocked from going live. If v1.3 had shipped by mistake, switching live traffic back to v1.2 is a one-line change.
Each version has an ID, a one-line note, a score on the same set, and a clear status. The history makes drift and recovery visible.
03Where It Fits

How it relates to nearby ideas.

What it is
A way of thinking about prompts: each one is an artifact with versions, scores, and a clear current state.
Pairs with
A prompt-versioning system that stores each version with its score, and a runtime that records which version answered each request so dips trace cleanly back to a change.
04When It Matters

When to reach for it.

  • Several people edit prompts: a shared version history is the only way to know whose change moved the score.
  • You depend on prompts in production: when quality dips, the prompt is the first place to look and the easiest place to revert.
  • You answer to compliance or audit: showing the exact prompt that produced any past answer means keeping its version live.
