Spec-Driven Engineering Workflow

The post-vibe-coding workflow. A human writes the spec, an agent implements and tests it, the human reviews the diff before anything ships.

Default in 2026 Human writes spec; agent implements + writes tests; human reviews diff before merge. Store spec, impl, and test as triplets in git. Never "vibe-code": every commit traceable to the spec it answered.
01The Idea

What is it?

A Spec-Driven Engineering Workflow is the discipline of writing the intended behavior down first, in plain English, before any code is generated. The agent implements against that spec; the human reviews the diff against that spec; the test suite proves the code keeps matching the spec.

06When to Use It

Pick the right shape.

Pick this over Vibe coding
Always, for anything that ships. "Vibe coding" (prompting until the demo works, no spec, no tests) is fine for throwaway prototypes and explicitly listed as an anti-pattern for production. Spec-driven is the cure.
Pick this over Pair-programming with the agent
When you can articulate the behavior up front. Pair-programming is the right shape for exploring an unknown; spec-driven is the right shape once you know what you want. The transition point is the moment you can write the spec.
Pick this over PR review of a human-written change
When the work is well-scoped and mechanical (refactors, CRUD endpoints, schema migrations, API client updates). A human-authored PR pays for an agent's time you did not have to. Save human authorship for the parts that need genuine judgment.
