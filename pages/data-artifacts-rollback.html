Rollback and roll-forward

When a release breaks, go back to the last good version (rollback), or fix forward with a new version (roll-forward).

01The idea

What is it?

Releases will go wrong. Rollback means flipping the live version back to the previous one in seconds. Roll-forward means leaving the broken release in place while you ship a small fix on top. Knowing in advance which one to do, and being able to do either quickly, is what turns a bad release into a small bump instead of a long outage.

02An example

A break, two ways to recover.

v8 went live and broke. Pick a recovery path.

09:00
ship
support-bot@v8 deployed to production.
09:14
break
Eval score drops. Users get malformed replies.
The team has minutes, not hours, to decide.
09:15
rollback
v7 is live again. Service restored in about a minute. v8 stays in the registry for later investigation.
Pick this when the break is bad and you do not yet know the cause. Fast, safe, no new code.
03Where it fits

Where it sits in the flow.

Rollback and roll-forward only work if every other version page has done its job: the registry has the old versions saved, the bundle pins say which version belongs with which, and the deploy system can flip the pointer or ship a tiny new build.
04When it matters

When to care about it.

  • The system is in front of real users and minutes of bad answers really hurt.
  • You ship often, so something will eventually go wrong and the recovery muscle has to be ready.
  • You need a clear rule for when to roll back versus when to fix forward, so no one freezes in the moment.
