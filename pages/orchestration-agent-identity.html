Agent Identity and Permissions

Each agent has its own badge and its own set of allowed actions. The system can prove who is asking, and only lets that agent do what it is meant to do.

01What It Is

Who is this agent, and what may it do?

Each agent gets a unique credential (identity) and a list of what it is allowed to touch (permissions), so every request it makes is checked before it goes through.

In plain words: "auth" (short for authentication and authorization) just means proving who you are and checking what you are allowed to do. Like a building pass: it says your name, and it opens the doors you have access to.
02An Example

Tap a request to see if it gets through.

Smallest set of permissions wins. Give each agent only what its job needs. If it gets tricked or goes off track, the blast radius stays small.
03Where It Fits

How it relates to nearby ideas.

What it covers
The check that runs around every tool call and every agent-to-agent message: is this caller real, and is this action on its list? It is a gate, not a tool.
Sits next to
Agent-to-agent protocols carry the identity; capability discovery lists what each agent offers; the gate decides which of those offers a given caller may actually use.
04When It Matters

When to reach for it.

  • Agents can touch real money, real customer data, or real systems and a wrong action would cost something.
  • Several agents share the same set of tools and you want a clear record of who did what.
  • You bring in agents built by an outside team and need to limit what they can reach inside your stack.

Sources
