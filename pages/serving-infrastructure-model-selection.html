Model selection at runtime

For each request, send it to the smallest, cheapest model that is good enough. Reserve the expensive one for the calls that truly need it.

01What Is It?

Right-size the model for each call.

You keep two or three models on hand: a small fast one, a medium one, and a large one. A quick check looks at the request (length, topic, complexity, who is asking) and picks the cheapest model that can handle it. The big model is only used when the small one would clearly fall short. Same product, but most calls land on the cheap tier, so the average cost per request drops a lot.

03Where It Fits

How it sits next to other ideas.

What it shapes
The runtime picks which model the call goes to, based on cost and latency targets. It does not change the prompt or the answer logic. Same in, just routed to a smaller engine.
Not the same as
Cascading (cheap first, then escalate if the answer looks weak) is a composition pattern with two calls. Picking the cheapest model that fits is one runtime decision before any call runs.
Sits on top of
A cost and quality budget. The runtime is applying a budget you set: how much quality you trade for how much money saved.
04When It Matters

When to reach for it.

  • Traffic is a mix of easy and hard requests. Most are easy. Pay accordingly.
  • You have a clear quality bar and can measure it, so you know when the cheap tier holds up.
  • Cost per call is starting to drive total spend, and one model size for everything is wasteful.
  • Skip this when every call is high-stakes or when quality differences are hard to measure: just use the strong model.
