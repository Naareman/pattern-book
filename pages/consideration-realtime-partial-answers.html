Checking partial answers

Read structured output before it is finished, so each field can be acted on the moment it is ready.

01What is it?

Read the shape as it grows.

Structured replies (JSON, key-value lists, function calls) often stream in the same way as plain text. A normal parser waits for the whole thing and falls over on anything that looks half-built. A partial-answer parser tolerates the unfinished shape: open braces, half-typed strings, missing commas. It keeps a running picture of what is complete, what is still being typed, and what is still expected. Each time a field finishes (the name, then the price, then the tags), the parser fires that field downstream so the page can render or the next step can begin. Latency drops because work starts on field one before field five exists.

03Where it fits

How it sits next to nearby ideas.

What it does
Parses a half-built reply and surfaces each field as soon as it is whole, so the next step does not wait for the whole document.
Pairs with
Often shows up with structured output and schema enforcement. The schema gives the parser its map of what to expect next.
Not this
It is a parser move, not a quality or safety judgement. Whether each field is correct or appropriate is a separate check.
04When it matters

When to reach for it.

  • Forms and dashboards that paint field by field so the user sees progress.
  • Tool calls where the first argument can fire a lookup while the others are still streaming.
  • Long structured outputs where the last bracket is many seconds after the first useful value.
