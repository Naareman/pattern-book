Side-Effect Sandboxing

Run risky code or actions inside a sealed playpen. If they go wrong, the damage stays inside the playpen instead of touching the real world.

01What is it?

A safe place to let it try.

Sandboxing runs the agent in a contained environment that cannot reach the network, file system, or database unless explicitly permitted, bounding the blast radius of any mistake.

02An Example

Agent runs Python in a walled garden.

Agent writes and runs code to analyze a CSV
import pandas as pd
df = pd.read_csv('upload.csv')
print(df.describe())
os.system('rm -rf /') # blocked
no internet no host files no production database CPU and memory capped wiped after the run
↓
The only thing that comes out is the result the agent returns. A mistake or a malicious instruction cannot touch your real systems.
03Where It Fits

Where it sits.

Common uses
Letting an agent execute code, open files, or browse the web without risking your real environment.
Different from
An approval gate. A gate stops the action and asks a person. A sandbox lets the action run, but in a place where mistakes cannot escape.
Stacks with
Combine with idempotency and rollback for actions that do need to reach the outside world: the sandbox handles the dangerous middle, the other patterns handle the safe-to-retry edges.
04When It Matters

When to reach for it.

  • The agent runs code it wrote itself, where you cannot fully predict what it will do.
  • The agent handles untrusted input (uploaded files, web pages, user-supplied prompts) that could carry hidden instructions.
  • You need a hard ceiling on damage from a buggy or hijacked agent: nothing inside the sandbox can reach what you care about.
